# CallCaption 0.21 计划（讨论稿）

- 日期：2026-11-12
- 状态：0.20.8-lab 已完成（双路 SFSpeech 可行）；下一步 0.21.0
- 基线：0.20.5（tag `v0.20.5-stable`，可回滚）；0.20.6 仅诊断
- 设备：iPhone 14 Pro Max，iOS 16.4，Dopamine rootless

## 1. 第二轮“慢得出奇”的定位

- 抓音正常：本地 tap 全程 `aq=22→487`、`frameAge=0.0s`、`tee` 119 秒整；远端 WAV 120 秒整。
- 问题在腾讯 WS 上行发送：握手 4–5 秒（第一轮 <1 秒）；两端 `backlog` 涨到 10000ms（ring 满）；`send lag` 3.1s/4.9s；本地字幕固定滞后约 10 秒。
- 两条独立 WS 同时变慢，说明是共享路径（Wi-Fi 之后的 WAN/VPN/国际出口/腾讯节点），不是单条连接、不是 tap、不是 WhatsApp、不是 DeepL/Google。
- 触发是网络波动，不可控；但“波动 → 10 秒积压 → 丢新音频”是 one-in-flight + ring 满丢新音频的设计放大的，这部分可控。

## 2. 腾讯 WS 上行是什么

两条独立的 WebSocket（每通电话 2 条），只做**语音识别**，不做翻译、不返回 TTS：

```
对方英文（WhatsApp 下行）
  AppProbe 抓 render → cc_remote_*.wav（WhatsApp Documents）
  → 守护进程 48k→16k、mono、s16
  → g_remoteRing
  → 每 200ms 发 6400 字节 PCM → wss://asr.cloud.tencent.com/asr/v2/...（16k_en）
  → 返回 JSON：partial / final 文本
  → SpringBoard：Google 翻译 → 中文字幕 + 本地中文 TTS → 下行混音

我方中文（麦克风）
  ATAudioTap 44.1k float → 16k s16
  → g_localRing
  → 每 200ms 发 6400 字节 PCM → 同端点（16k_zh）
  → 返回 JSON：partial / final 文本
  → SpringBoard：DeepL 翻译 → 英文字幕 + 本地英文 TTS → 上行混音
```

关键参数与逻辑：

- 格式：16k / 单声道 / 16bit PCM；200ms = 3200 samples = 6400 bytes。
- 速率：32KB/s（256kbps）/方向；双向 64KB/s（512kbps）。10 分钟通话约 19.2MB。
- ring 不足 3200 samples 时补零，保持 1:1 连续流，供服务端 VAD 使用。
- 0.20.0/0.20.5：同一时刻只允许 1 包在途（one-in-flight）；发送吞吐 ≈ 1/RTT，RTT 超过 200ms 就必然落后。
- 握手成功时清空 ring，丢掉握手期间的旧音频，避免整通电话带固定延迟。
- 返回只有文本（`voice_text_str`、`slice_type`、`index`）；翻译和 TTS 都在本机。
- 这条 WS 不是通话本身：WhatsApp 的通话音频走 WhatsApp 自己的链路；这里只是把每一路声音复制一份上云做识别。

## 3. 翻译策略

- 只用 DeepL / Google，文本翻译，不上传音频。
- 按方向独立配置：
  - 对方 → 我（en→zh）：默认 Google；
  - 我 → 对方（zh→en）：默认 DeepL。
- 每个方向主端点 + 另一个作回退；AI 仅最后兜底且默认不启用。
- 不用阿里、不用 Qwen 翻译、不做 SI。
- 文本请求是离散的：某句慢只影响该句，不会积压成 10 秒音频队列。

## 4. 路线

### 0.20.7 云端保险（仍走腾讯 ASR）

- 自适应 2 包在途：正常 1 包；backlog >1.5s 才允许第 2 包；仍 200ms 一 tick、不突发追回。
- backlog 熔断：持续 >4s（5 秒确认）→ 丢积压、跳到最近 0.3s，30 秒滞回。
- 诊断：握手毫秒、每 5 秒 txPackets、解析到的腾讯 IP、send lag 分布。
- tap 断流重启阈值做成设置项，默认 4 秒。
- 语气词：接通前 3 秒忽略；之后只上字幕、不 TTS；收窄“长度≤2”规则。

### 0.20.8-lab（离线实验，不打真电话）

- WAV 喂 SFSpeech：A 对方单路 / B 我方单路 / C 双路同时，各 3 分钟。
- 用 0.20.5 的 `remote16k.wav`/`local16k.wav`，验证：
  - on-device 连续 94 秒会不会在 60 秒附近报 203/1110；
  - 双进程是“按进程锁”还是“全局单实例锁”；
  - 同一段音频 SFSpeech vs 腾讯的字准率；
  - 首字延迟、CPU、thermalState。
- 结论决定 0.21.0 是否值得做、0.22.0 是否直接上 Sherpa-ONNX。
- 触发：设置 → CallCaption → 诊断 → 实验 A/B/C，各约 150 秒；结束后导出 `probe.log` 搜 `LAB`。
- 前置：实验用上一通留下的 `local16k.wav` / `remote16k.wav`；下一通电话 arm 时会删除它们，所以先实验再打电话。

**实测结果（2026-11-12，probe(28).log）**

- C 双路：SpringBoard remote + 守护进程 local 同时跑 150 秒，`err=0`、`sessions=1`，没有 1110/301；60 秒附近没有断流。
- A/B 单路：同样 `err=0`、`sessions=1`，可作为单路基线。
- 温度：双路 `thermal=1 (Fair)`，单路 `thermal=0 (Nominal)`，低电量模式关。
- 本地 SFSpeech 质量：明显好于腾讯 600ms VAD 的碎片——`总体状态还行，延迟比较低` 一整句，腾讯切成 `呃，总体状态。/ 还行。/ 延迟。/ 比较低。`
- remote 首字 1.85 秒；local 首字 17.6 秒是 WAV 开头约 17 秒静音，不是引擎延迟。
- 结论：**`corespeechd` 是按进程隔离，双本地 SFSpeech 可行**；不需要为了“锁”去上 Sherpa-ONNX/Vosk。

### 0.21.0 我方本地（只改一个变量）

- 对方：保持腾讯 ASR + Google（与第一轮相同）。
- 我方：守护进程内 on-device SFSpeech（读 `local16k.wav`，强制 `requiresOnDeviceRecognition=YES`），最终文本通过 `LI|`/`LQ|` 交给 SpringBoard，DeepL + 本地英文 TTS 不变。
- 本地腾讯 WS 关闭；上行从 2×32KB/s 降到 1×32KB/s（只剩对方那条）。
- 设置项 `TencentLocalEngine`：`sfspeech`（默认）/ `tencent`（回退）。
- 验证指标：首字、1110/301、断句碎片、55 秒轮换、长通话、发热。

**0.21.0 实测（2026-11-12）**

- 启动正常：`tencent asr started remote=1 local=0 localEngine=sfspeech`；`local asr: start onDevice=1 auth=3`；`task start supportOD=1`。
- 本地前 55 秒有字幕，但发现三个工程问题：
  1. 20:02:43 Tap 首通停摆重挂，`CCLocalTeeOpen` 用 `fopen("wb")` 截断 `local16k.wav`；本地 ASR 检测到文件变短，重置 text/delivered，重挂后的第一句拼坏。
  2. 55 秒轮换后第二个 SFSpeech task 只出了“不出字幕了”，之后 53 秒用户有说话但本地零字幕（WAV 能量确认有语音）；轮换后的 task 停摆。
  3. 单字碎片“路”被 1.8 秒静音分支送出，DeepL 译成 “Road” 混进上行。
- 对方腾讯通道正常：backlog 650–1200ms，无 drop。
- 结论：“去电不如来电”是本地 SFSpeech 路径的三个工程问题，不是引擎本身。

**0.21.1 修复**

- `CCLocalTeeOpen`：existing>44 时用 `r+b` 追加，不再截断；Tap 重挂不再重置本地 ASR 文本。
- 55 秒轮换 → 480 秒（lab 已证明 on-device 单会话 150 秒无错）；避免第二个 task 停摆。
- 单字碎片不送翻译/TTS；保留有意义的一字回答（对/好/是/行/嗯/啊/哦）。
- 增加 `local asr: partial` 日志，下一次能看清 task 是否在出字。

**0.21.1 实测（2026-11-12 晚）**

- `local tee open ... (append, no truncate)` 生效，Tap 重挂不再截断文件。
- 但守护进程内 SFSpeech 在真实通话中被系统/音频会话饿死：
  - task 20:54:22 启动，**128 秒内零 partial**；
  - local16k.wav 在 4–6s、10–12s、20–22s、27–28s、34–37s 都有明显人声，ASR 没出字；
  - 128s 后才开始出 “七 / 7:00 / 去年一直都没有怎么 / 偶尔出现一下下水平话太严重，整个测试失败”，质量很差；
  - 对方腾讯通道全程正常（backlog 200–640ms）。
- 结论：不是文件/端点问题，是 **daemon 进程内的 SFSpeech 在通话负载下拿不到 corespeechd 的处理时间**。lab 没有真实通话负载，所以没暴露。

**0.21.2 修复**

- 本地 SFSpeech 放回 **SpringBoard**（0.17.0 真实通话已验证可用），只跑一路，不触发双路互杀。
- 守护进程内 `CCLocalASR` 停用；对方继续腾讯 ASR。
- SpringBoard 本地流强制 `onDevice=YES`，忽略 `CloudASR`，避免走 Apple 云端。
- SpringBoard 55 秒轮换 → 480 秒（on-device 无 60 秒硬限制）。
- 设置 `TencentLocalEngine=tencent` 仍可回退守护进程本地腾讯。
